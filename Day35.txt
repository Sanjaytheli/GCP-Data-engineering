Bigquery Architecture:
----------------------

==> Google bigquery architecture is designed to handle large scale data processing and analysis in distributed , serverless and highly scalable manner.
==> It seperates storage and compute, which allows efficient querying and analysis on massive datasets.

storage layer [Colossus]:
--------------------------
==> Bigquery data storage is handle by a distributed file system called as "capacitor".
==> with in Colossus whatever data it is going to store that data will store in "Columnar format", which enables efficient compression and minimizes the amount of data read during queries.
==> capacitor automatically manages data distribution and replication across multiple nodes for high availability and durability.

compute layer [DREMEL]:
---------------------
==> Bigquery compute layer includes the execution of sql queries and other data processing tasks.
==> it uses a technique called as dynamic runtime filter (DRF) to distribute query execution across a fleet of workers called as "slots".
==> DRF helps parallel execution of your queries and data processing, with this we can complete all our compute operations in very very fast manner.

step1: whenever you run your queries those queries will go to "ROOT SERVER" with in dremel component
	a) root server will parse your entire query [select , * , from , customer]
	b) root server will verify all keywords are correct or not , and also root server will verify give table and column names are present in bigquery or not.
	c) if any keywords are wrong or if any table or columns are not available, then root server will send Error message.
	d) this root server will store all the metadata of our tables (table name, column names, datatypes..)
	e) if your query is not having any kind of issues, then Root server will prepare the plan to run your query.
		plan:
			t1:
			t2:
			t3:
			t4:
	f) once plan is ready then this plan will send to "Leaf nodes"
	
Leaf nodes: 
 - Leaf nodes are responsible for storing and processing the data
 - They execute all the queries in parallel manner and it will store all the intermediate results of our sql queries
 
 Leaf nodes ==> data processing operations ==> Jupyter ==> Colossus
 - Leaf nodes will send all these intermediate results to the "mixer nodes"
 
Mixer nodes:
 - Mixers play a role to combine the intermediate results or it aggregate all the intermediate results which it is getting from different leaf nodes, with that it will create final result 
 - this final result will send back to root server, then from root server this result will display in console or sdk shell.
 
 submit query ==> Root server ==> Plan ==> Leaf nodes ==> intermediate results ==> mixer nodes ==> final result ==> root server ==> console/sdk shell
